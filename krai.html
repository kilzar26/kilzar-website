01 / Core thesis

The vehicle is not
one diagnostic session.

PERSISTENT MEMORY

History as system state

Symptoms, observations, decoded evidence, repairs, outcomes, and learned baselines stay associated with the specific vehicle over time.

PROVENANCE

Evidence behind conclusions

Diagnostic hypotheses should remain traceable to the evidence and transformations that produced them, with uncertainty kept visible.

REPAIR-EFFECT LEARNING

Verify after intervention

A repair is not treated as the end of the story. KRAI's target loop compares what happened afterward and updates the vehicle baseline.

02 / Current development focus

Baseline → deviation → evidence → diagnosis →
intervention → verification.

The active engineering priority is making this longitudinal case reproducible before expanding KRAI's feature surface.

03 / Safety and authority

Conversation can propose.
Guardian decides.

READ-ONLY TODAY

No public vehicle control

Development diagnostic interfaces are read-only today; no public vehicle-control features are offered while evidence handling and diagnostic reasoning are validated.

AUTHORITY GATING

Intent is not permission

Any future vehicle interaction must pass deterministic capability, authorization, safety, and audit boundaries separate from conversational personality.

FAIL CLOSED

Safety before convenience

Future action paths are intended to require explicit capability checks, independent confirmation where appropriate, watchdogs, and auditable execution.

04 / Local-first direction

Useful when the cloud
is not the whole answer.

KRAI development prioritizes keeping important vehicle history and core reasoning close to the user where practical. This is an architectural direction, not a claim that every planned capability is already fully offline.
